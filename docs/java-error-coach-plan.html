三个最容易照抄错的地方（2026-11 核实）：
① 老教程里的插件 ID 是 org.jetbrains.intellij（1.x），已废弃；2024.2+ 必须用 2.x 的 org.jetbrains.intellij.platform（当前 2.19.0，以官方文档为准）。写法完全不同，别混着抄。
② 平台与 Java 版本绑定：2024.2–2026.1 需 Java 21，2026.2+ 需 Java 25。选 2025.3 就是选 JDK 21。
③ DeepSeek 旧模型名 deepseek-chat / deepseek-reasoner 已于 2026-07-24 弃用，现在是 deepseek-v4-flash / deepseek-v4-pro；Base URL https://api.deepseek.com（OpenAI 格式，不加 /v1）。
v2.1 更正两处（详见第 6 节）：① untilBuild 官方强烈建议不要设置，只写 sinceBuild 即可开放后续所有构建；② 2025.3（分支 253）起官方产品类型调整，intellijIdeaCommunity() 只适用于更早版本，应改用 intellijIdea()。v2 初版这两处不够准确，已按官方文档更正。

最小构建脚本骨架（照官方 2.x 写法，具体版本以官方文档为准）

plugins {
    id("java")
    id("org.jetbrains.intellij.platform") version "2.19.0"
}
repositories {
    mavenCentral()
    intellijPlatform { defaultRepositories() }   // 平台依赖来自 JetBrains 仓库
}
dependencies {
    intellijPlatform {
        intellijIdea("2025.3")                   // 2025.3+ 用统一类型；别写 latest
        bundledPlugin("com.intellij.java")       // 需要读 Java 文件时声明
    }
    implementation("com.fasterxml.jackson.core:jackson-databind:2.x.x")
    testImplementation("org.junit.jupiter:junit-jupiter:5.x.x")
}
intellijPlatform {
    pluginConfiguration {
        ideaVersion { sinceBuild = "253" }       // 只设下限，不要写 untilBuild
    }
}

这段代码不要求你现在看懂；第 2–3 周的学习路径会逐行拆给你。注意 sinceBuild 与编译目标是两件事：前者声明产物能装到哪些 IDE，后者决定用哪套 API 编译 —— 详见第 6 节。

3. 项目规格：做什么，不做什么

一句话：在 IDEA 里选中一段 Java 报错，右键「用报错教练讲解」，右侧面板给出中文解释、关联知识点和三级递进提示，并自动存进个人错题库。

三条用户故事：

  1. 作为学 Java 的学生，我遇到看不懂的堆栈时，选中它点一下，就能看到「这报错在说什么」的大白话解释。
  2. 作为想学会而不是想抄答案的学生，我先看到提示，点「再给一层」才看到更具体的思路，全程不出现可直接复制的完整修复代码。
  3. 作为会重复踩同一个坑的学生，我能在错题库里看到「NullPointerException 出现 7 次」，并回看当时的解释。

做（P0，必须完成）

  • 仅 Java：编译错误 + 高频运行时异常
  • 选中 Run 窗口文本 → 右键触发（接受不自动，这是明确的取舍）
  • 结构化讲解卡片：错误类型 / 人话解释 / 知识点 / 三级提示 / 自查清单 / 置信度
  • 6 类错误 → 专属 Skill 模板 + 20 条本地规则库（断网可用）
  • 超时、429、非法 JSON、无网四条失败路径的降级
  • Key 安全存储、最小上下文、路径脱敏
  • 本地错题库 + 知识点频次统计
  • ≥15 个单测 + 30 例手工评测表

不做（写进 README 的 Scope）

  • 自动捕获全部控制台输出 / 全项目上下文（P2，做完再说）
  • 一键改代码、apply patch
  • 多语言、Kotlin、其他 IDE
  • 账号、云端同步、后端服务、数据库
  • 登录鉴权、插件市场签名与上架
  • 模型微调、RAG、知识图谱
  • 花哨 UI、主题、动画
  • 全版本真机兼容矩阵（L2，选做；L0 声明与 L1 静态验证是必做）

「不做清单」不是偷懒，是范围管理 —— 单人项目失控几乎都源于没写这一栏。

4. 架构与模块设计

分四层。分层的意思：让「界面」「业务逻辑」「外部调用」互不直接依赖，改其中一层不会连锁改其他层，也才能单独测试。

层包 / 类（建议）职责
UI 层ui.ExplainAction
ui.CoachToolWindowFactory
ui.ExplanationPanel		右键菜单动作、结果面板、「再给一层」按钮。只负责展示，不写业务逻辑
应用层app.ExplainService
app.ContextAssembler		编排一次讲解的完整流程：取选中文本 → 组装上下文 → 路由模板 → 调模型 → 归档
领域层domain.ErrorClassifier
domain.SkillRegistry
domain.RuleBook
domain.Explanation		纯 Java 逻辑，不依赖 IDE 和网络：错误分类、模板选择、离线规则、结果数据类。这一层最好测
基础设施层infra.DeepSeekClient
infra.SettingsService
infra.MistakeRepository
infra.Cache		HTTP 调用、配置与 Key、持久化、缓存。所有「不确定的外部世界」关在这一层

一次讲解的数据流（五步）

  1. 捕获：AnAction 从 Editor.getSelectionModel() 拿选中文本；空选则提示「请先选中报错」。
  2. 组装：只取必要最小集 —— 当前文件名、光标附近 ±20 行、堆栈点名的文件片段、JDK 版本；去掉绝对路径、姓名、学号。
  3. 路由：正则先判错误类型（NPE / 数组越界 / 类型转换 / 类找不到 / 语法错误 / OOM），命中本地规则库就直接返回，不调模型；未命中才套对应 Skill 模板。
  4. 推理：后台线程（不要在 UI 线程发网络请求，否则 IDE 会卡住）调用 DeepSeek，强制 JSON 返回，带超时与重试。
  5. 呈现与归档：切回 UI 线程渲染卡片；结果写入错题库；相同文本哈希命中缓存则不重复请求。

结构化输出契约（设计阶段就要定死）

模型必须返回固定 JSON，而不是一大段自由文本 —— 这样 UI 才能分层展示、错题库才能统计、测试才能断言。

{
  "error_type": "NullPointerException",
  "plain_explanation": "你调用了一个还没有指向任何对象的方法…",
  "knowledge_points": ["引用与对象", "null 的含义", "初始化时机"],
  "likely_line": "Main.java:12",
  "hints": [
    "level 1: 先看第 12 行，哪个变量可能是 null？",
    "level 2: 检查这个变量是否只在 if 分支里被赋值",
    "level 3: 考虑调用前判空，或给构造器一个默认值"
  ],
  "self_check": ["打印该变量的值", "确认构造顺序"],
  "confidence": 0.86
}

提示词里写死三条约束：① 面向只学过一个学期 Java 的新手，先讲概念再讲修法；② 严禁输出完整可复制的修复代码，最多 3 行局部示例；③ 不确定时降低 confidence 并明说「需要看更多上下文」。

三条必须写进设计的失败路径

场景期望行为
无网 / 超时 / HTTP 429 / 余额不足不白屏、不吞异常：展示本地规则库最接近的一条 + 明确提示「已保存，稍后可重试」
模型返回非法 JSON 或字段缺失解析层抛出可识别的异常 → 降级为纯文本展示，并把该条记入 badcase 列表
用户没选文本 / 选中的不是报错友好提示并给出示例，不发起请求、不消耗 token

关键平台 API 对照（第一次见到时的白话解释）

名词白话解释
plugin.xml插件的「户口本」。类写好了不算数，必须在这里登记，IDE 才会加载它

5. 工程规范：让「练手」练到点上

Git 与提交

  • 一条主线 main 始终保持可编译；每个功能开短分支，做完合并
  • 提交信息写「为什么」而不只是「改了啥」：feat: 增加 NPE 模板，避免直接给出修复代码
  • 每周打一个 tag：v0.1-hello、v0.2-loop…
  • 至少认真做一次 git revert，体会版本管理真正的价值

编码与依赖

  • 不吞异常：捕获后要么处理、要么包装后上抛，禁止空 catch
  • 日志分级，但绝不打印 Key、代码片段、请求体原文
  • 配置外置：base_url、model、超时、开关都进设置页，不写死
  • 每加一个依赖都要能说清「为什么不能用 JDK 自带的替代」
安全底线：API Key 只存 CredentialStore；只上传「必要最小上下文」并做脱敏；设置页提供「本次不上传代码」开关；README 里写清楚数据会发到哪里、发了什么。这几条练的是工程习惯，比功能本身更值钱。

6. 兼容性策略（v2.1 补充）

先厘清一个容易混淆的点：「锁定一个版本编译」不等于「只能装在那一个版本上」。这是两个独立的旋钮 —— 编译目标（platformVersion）决定用哪套平台 API、哪个 JDK 编译；兼容声明（sinceBuild）决定产物允许被装到哪些 IDE 上。规划锁的是前者，后者应当开放。

层做什么本项目
L0 声明层只写 sinceBuild = "253"，不写 untilBuild（官方强烈建议：不设上限即声明兼容 253 及之后所有构建，必要时日后通过 Marketplace 收窄）。跨多版本支持时用最低支持版本编译，这是官方建议，在版本间 Java 级别不同时更是强制要求。必做 · W1
成本近零
L1 静态验证./gradlew verifyPlugin 运行官方 Plugin Verifier，检查二进制兼容性、plugin.xml 结构与项目配置；配套还有 verifyPluginStructure、verifyPluginProjectConfiguration。2.15.0 起默认更严：兼容性问题、Internal API 误用、Override-Only API 误用会直接让构建失败；2.14.0 起未显式配置验证目标时自动按 recommended() 从声明范围解析 IDE，也可用 create() 精确指定单版本做冒烟检查。必做 · W11–12
一条 Gradle 命令
L2 真机矩阵切换 platformVersion 用 runIde 在不同版本沙箱 IDE 里跑一遍核心流程，或把 zip 装到装有不同 IDEA 版本的机器上手工验证。选做
数小时

这个项目对版本的依赖到底大不大

偏小。它只用到平台最稳定的一批基础 API（AnAction、ToolWindow、Service、PersistentStateComponent、CredentialStore、SelectionModel），网络与 JSON 全在 JDK 侧（HttpClient + Jackson），没碰 PSI、没用 @Internal / @Experimental 标注的 API、也没依赖 Java 语言插件内部实现。所以一次「2025.3 + Java 21」编译，大概率能覆盖 2025.3–2026.1 这一档（同为 Java 21 级别）。

但「偏小」不等于「免验证」：① 平台每个大版本都有不兼容 API 变更（例：2026.3 移除 Kotlin UI DSL 1.0）；② 2026.2+ 平台自身要求 Java 25，若把编译目标改到那一档就必须换 JDK 25（社区已出现 class file 69.0 与 65.0 不匹配的编译报错）；③ Java 21 的字节码能在 Java 25 运行时上跑，但「能跑」不等于「API 没变」。所以 L1 的作用，就是把「大概率没问题」变成一份可检查的报告。

范围结论

本项目做到 L0 + L1：声明开放、跑一次 verifyPlugin 并读懂报告；L2 与「为每个大版本单独出产物」不列入范围（已写进不做清单）。README 里放一张三列兼容表：已验证 / 声明支持 / 未验证，诚实区分三者，比含糊写「支持新版本」更专业。

v2.1 修正记录（保留而非静默改掉）：① 初版写「写清 untilBuild」→ 改为不设 untilBuild；② intellijIdeaCommunity("2025.3") → intellijIdea("2025.3")（IC / PC 产品类型仅适用于 2025.3 之前）；③ Gradle 插件示例 2.18.1 → 2.19.0（以官方当前文档为准）。把修正写进文档，是因为可追溯的变更记录本身就是第 07 环节要练的东西 —— 规划允许被现实修正，关键是改了什么、为什么改，得看得见。

单元测试错误分类、Skill 路由、JSON 解析、提示词渲染、缓存哈希、脱敏领域层是纯 Java，用 JUnit 5 直接测，不需要启动 IDE
集成测试HTTP 调用、超时、429、非法 JSON、降级路径用 JDK 自带 HttpServer 在本地起一个「假 DeepSeek」，返回预设 JSON；不花钱、不依赖网络、可重复
手工评测30 个真实 Java 报错，记录「原因是否说对 / 知识点是否命中 / 有没有违规给完整代码」一张表格，W1 开始收集，W11 集中跑
回归清单每次改提示词或改代码后，重跑同一批用例把 30 例存成资源文件，避免「改好一个、弄坏三个」

用假接口测网络代码，是这个项目里最值得练的一招：它逼你把「调用外部服务」和「业务逻辑」分开，而这正是分层设计的目的。

8. 14 周里程碑

按每周 10–12 小时估算。愿意多花时间就把每周拆成两周，不要压缩环节，只拉长节奏。

9. 风险与卡点预案

大概会卡在哪怎么办
Gradle 同步失败 / 依赖拉不下来确认用的是 2.x 插件 ID、defaultRepositories()、网络可达；先只跑 runIde，别急着加依赖
沙箱 IDE 起不来或插件没出现九成是 plugin.xml 没登记、JDK 版本与目标平台不匹配、或 sinceBuild 写错；先跑官方示例对照
IDE 界面卡死网络请求放后台线程，UI 更新切回 EDT；这是插件开发最常见的新手错误
模型返回乱七八糟强制 json_object、字段校验、置信度阈值、badcase 回流；高频错误优先走本地规则库
费用 / 限流缓存 + 本地规则库兜底；deepseek-v4-flash 单次约 0.003 元，正常练手基本花不到 10 元
一个人没动力每两周一个可演示产出；每周打 tag；把「这周学会了什么」写进提交记录，用可见进展对抗长期任务
新版 IDE 显示「不兼容」检查是否误写了 untilBuild 上限、sinceBuild 是否用了不存在的分支号；构建号必须是真实值，Plugin Verifier 会校验
verifyPlugin 报 Internal / Override-Only API说明用到了不该用的内部 API；换回公开 API 重写该处，不要靠调低 failureLevel 掩盖
把编译目标误升到 2026.2+那一档要求 JDK 25，会出现 class file 版本不匹配；练手阶段保持 2025.3 + JDK 21，需要跨档时单独开分支
「卡住两小时」规则：同一个环境问题连续两小时没进展，就停下来，把现象、报错、试过的方法写成一段文字（这本身就是预研记录），然后换一条路或第二天再看。不要在环境配置上耗尽热情 —— 它不属于你要练的核心能力。

10. 最终交付清单与验收

  • 可安装的插件 zip（含兼容范围说明与 README 三列兼容表）
  • verifyPlugin 输出报告（无兼容性错误，警告已逐条说明）
  • 源码仓库：清晰提交历史、每周 tag、.gitignore、v1.0 发布标记
  • README：这是什么、怎么装、怎么配 Key、数据发到哪里、已知限制、Scope（不做清单）
  • 架构图 + 模块职责表 + JSON 契约（设计文档）
  • 测试：≥15 个单测、假接口测试、30 例评测表与回归清单
  • CHANGELOG、3 分钟演示录屏、一页复盘笔记

七条验收标准：① 八环节证据齐全；② 另一台机器可安装并跑通；③ verifyPlugin 无兼容性错误，README 兼容表如实区分「已验证 / 声明支持 / 未验证」；④ 断网时高频错误仍可讲解 ≥20 类；⑤ 完整修复代码泄露 = 0；⑥ 从右键到出结果 ≤5 秒且不卡 UI；⑦ 能白板讲清数据流与三条失败路径。
