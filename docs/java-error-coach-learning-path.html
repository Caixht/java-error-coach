五条学习原则（比知识点更重要）

  1. 先跑通，再理解。第一遍照官方文档把 Hello World 跑起来，第二遍才逐行问「这行在干嘛」。顺序反了会卡死在概念里。
  2. 每个知识点必须有一个能运行的结果。看懂 ≠ 会写。看完 HttpClient 就亲手发一次请求，看完 plugin.xml 就亲手登记一个菜单项。
  3. 不整段抄代码。可以读官方示例、可以查 API，但要自己敲一遍并改点东西。你练的是「能讲清数据流」的能力，抄来的代码讲不清。
  4. 官方文档优先。插件 SDK 的 API 变动很快，2024 年之前的博客大概率失效；遇到冲突以 JetBrains 官方文档与示例仓库为准。
  5. 卡住两小时就停。把现象、报错、试过的方法写成一段文字（这本身就是工程记录），然后换路或第二天再看。别在环境配置上耗尽热情。

S0 · Java 21 与命令行基本功

S0把「会写 Java」变成「能写工程代码」W1–2 · 对应环节 01 / 02

目标：能不用 IDE 自动补全，独立写出一个读文件、发 HTTP、解析 JSON 的小命令行程序。这是后面所有代码的底座。

要学的知识点（括号里是白话）
  • 集合、泛型、异常、IO —— 工程代码里每天都在用
  • Lambda 与 Stream：写过滤、分组、统计时用得上
  • record / sealed / switch 模式匹配（Java 21）：用 record 当数据类，比手写 getter 干净得多
  • java.net.http.HttpClient：JDK 自带的 HTTP 客户端，不用引第三方库
  • Jackson ObjectMapper：JSON ↔ Java 对象互相转换
  • 包结构、类职责、接口与实现分离
为什么现在学

插件的领域层（错误分类、模板路由）是纯 Java；基础设施层的 HTTP 与 JSON 也全靠这些。这里省下的时间，后面会成倍还回来。

动手任务
  • 写一个命令行程序：读一个文本文件 → POST 到本地假接口 → 把返回的 JSON 映射成 record 并打印
  • 故意传一段坏 JSON，看它怎么抛异常、你怎么处理
  • 用 try/catch 之外再试一次「包装后上抛」，体会异常分层
检验标准（学会了就打勾）
资料

Oracle Java Tutorials（官方，选 Collections / Exceptions / Lambda 三章即可）；JDK 21 HttpClient 与 ObjectMapper 官方 Javadoc / README。不必通读，用到哪查到哪。

预期卡点

JDK 版本与 IDE 里配置的 JDK 不一致；Jackson 版本与 Java 21 的兼容性。先把 java -version 和 ./gradlew -v 两个输出看清楚再往下走。

S1 · Gradle 与 Git

S1让构建和版本管理变成肌肉记忆W2–3 · 对应环节 02 / 04

目标：能逐行解释自己项目的 build.gradle.kts，并能在 Git 里安全地回滚一次。

要学的知识点
  • Gradle Wrapper 是什么（把构建工具版本锁进仓库，换机器结果一致）
  • plugins / repositories / dependencies 三个块各管什么
  • 常用任务：build、runIde、buildPlugin、test
  • ⚠️ 2.x 插件 ID 是 org.jetbrains.intellij.platform；老教程的 org.jetbrains.intellij（1.x）已废弃
  • Git：init / add / commit / branch / merge / tag / revert / .gitignore
  • 提交粒度：一次提交只做一件事，信息写「为什么」
  • sinceBuild 声明最低兼容 IDE；官方强烈建议不写 untilBuild（不设上限即可兼容后续所有构建）
  • 构建号必须是真实分支号（2025.3 → 253），编造的值会被 Plugin Verifier 判定无效
为什么现在学

插件开发的第一道坎从来不是 Java，是构建脚本。把它搞懂，后面 12 周都顺。

动手任务
  • 从零建一个 Gradle Java 项目，跑通 ./gradlew build
  • 生成插件项目骨架，跑通 ./gradlew runIde（会启动一个沙箱 IDE）
  • 给仓库加 .gitignore（排除 build/、.idea/、.gradle/、任何含 Key 的文件）
  • 故意提交一次错误改动，再用 git revert 撤掉
检验标准
资料

IntelliJ Platform Gradle Plugin 2.x 官方文档（配置写法以此为准）；Gradle 官方 Getting Started；Pro Git 中文版前 3 章。

预期卡点

依赖拉不下来；误设了 untilBuild 上限导致新版 IDE 装不上；sinceBuild 写成编造的分支号；把 1.x 与 2.x 的写法混抄。另注意 2025.3（253）起官方产品类型调整，intellijIdeaCommunity() 只适用于更早版本，应使用 intellijIdea()。对照官方示例逐字检查，别凭印象改。

S2 · IntelliJ Platform SDK 基础

S2理解「插件是怎么挂进 IDE 的」W3–5 · 对应环节 02 / 03 / 04

目标：能说清「我写的类」到「IDE 里的菜单项」之间发生了什么，并做出一个真实可用的面板。

要学的知识点
  • plugin.xml（插件的户口本）：ID、依赖、Action 与扩展点登记
  • 扩展点 EP：IDE 预留的插槽，你注册实现，IDE 在对应时机调用你
  • AnAction 与 AnActionEvent：拿 project、editor、选中文本
  • ToolWindowFactory 与面板；Service（IDE 管理的单例）
  • EDT 与后台线程：耗时操作绝不能放在画界面的线程上
  • SelectionModel / Document：读取编辑器里的文本
为什么现在学

W3–4 要打通端到端闭环，这一阶段的知识就是闭环的骨架。

动手任务
  • Hello World Action：右键菜单点一下，在面板显示当前选中的文本
  • 做一个 ToolWindow，含一个「再给一层」按钮
  • 把一次网络请求放到后台线程，观察放错线程时 IDE 卡住的现象（值得故意试一次）
  • 画一张图：用户点击 → Action → Service → 面板，标出每一步在哪个线程
检验标准
资料

IntelliJ Platform Plugin SDK：Actions、Tool Windows、Services、Threading Model 四章；官方 intellij-sdk-code-samples 示例仓库（先看 action_basics 与 tool_window 两个样例）。

预期卡点

菜单不出现（多为 registration 写错或依赖未声明）、面板空白、线程用错导致界面冻结。先跑通官方样例，再把自己的逻辑一点点换进去，不要一次改太多。

S3 · HTTP、JSON 与提示词工程

S3把「调 AI」变成一项可靠的工程能力W5–8 · 对应环节 04

目标：不再把大模型当魔法，而是当成一个「不稳定、会超时、会返回脏数据」的外部依赖来对待。

要学的知识点
  • OpenAI 兼容的 chat completions 协议：URL、Header、请求体、响应体
  • response_format: {"type":"json_object"} 强制结构化输出
  • 超时、重试与退避、HTTP 429 与余额不足的处理
  • 提示词设计：角色约束、few-shot 示例、输出格式、置信度字段
  • 「分层提示、禁止给完整答案」这类约束怎么写进 prompt 才真的生效
  • 脱敏与最小上下文：只发必要片段，不发整个项目
为什么现在学

这一阶段决定项目是「能跑的 Demo」还是「能用的软件」。四条失败路径的价值，往往比主流程更能体现工程水平。

动手任务
  • 用 JDK 自带 HttpServer 起一个假 DeepSeek，返回预设 JSON
  • 先用假接口跑通全链路，再换成真 Key 调一次真实请求
  • 写 6 类错误的 Skill 模板，各配 2–3 个 few-shot 示例
  • 故意让假接口返回非法 JSON、超时、429，验证降级是否生效
检验标准
资料

DeepSeek 官方 API 文档（模型名、价格、JSON Output）。注意 2026 年现状：deepseek-chat / deepseek-reasoner 已于 2026-07-24 弃用，现在用 deepseek-v4-flash；Base URL 为 https://api.deepseek.com。

预期卡点

照老教程写错模型名导致 404；把 prompt 写得太长导致输出不稳定；把 Key 硬编码进源码。这三条是这个项目最典型的坑，提前避开。

S4 · 测试与工程化

S4从「我觉得没问题」到「我验证过」W8–11 · 对应环节 05

目标：写出能重复运行的测试，并用一张评测表判断 AI 输出到底好不好。

要学的知识点
  • JUnit 5：断言、参数化测试、测试命名、before/after
  • 测试替身：为什么用假接口而不是真调模型（省钱、可重复、可制造故障）
  • 回归测试：改一处后重跑同一批用例，防止「改好一个弄坏三个」
  • 评测思维：给 AI 输出定义可打分的指标，而不是凭感觉
  • PersistentStateComponent：让 IDE 托管状态，重启后自动恢复
  • 缓存、幂等、配置外置、日志分级
为什么现在学

分层设计是否真的做对了，测试会立刻告诉你：如果领域层必须启动 IDE 才能测，说明分层没做好。

动手任务
  • 给错误分类、Skill 路由、JSON 解析、脱敏各写 3–4 个单测
  • 把 30 例真实报错整理成资源文件，写一张评分表
  • 记录 5 个 badcase，说明「为什么错、模板怎么改」
  • 实现错题库持久化，重启沙箱 IDE 后数据仍在
检验标准
资料

JUnit 5 User Guide；IntelliJ Platform SDK「Persisting State of Components」与「Persisting Sensitive Data」两章。

预期卡点

把 IDE 相关代码混进领域层导致无法单测 —— 这时回头改分层，别硬写测试。这个「被迫重构」的瞬间，正是练手最值钱的收获。

S5 · 构建交付与复盘

S5让陌生人也能装上、用上、看懂W11–14 · 对应环节 06 / 07 / 08

目标：完成从「我这台机器能跑」到「别人也能跑」的最后一公里，并诚实总结这一轮。

要学的知识点
  • buildPlugin 产物结构；sinceBuild 开放上限的兼容区间（不要写 untilBuild）
  • Plugin Verifier：verifyPlugin 做二进制兼容性检查；@Internal / @Experimental 等 API 状态标注为什么不能随便用
  • 「已验证 / 声明支持 / 未验证」三列兼容表怎么写才诚实
  • 从磁盘安装插件（Install Plugin from Disk）的完整流程
  • 语义化版本、CHANGELOG、tag 与发布标记
  • 技术文档写作：README 要写给「完全没参与过项目的人」
  • 演示录屏：只讲一条主流程 + 一个失败降级，3 分钟足够
  • 复盘方法：估算偏差、卡点耗时、badcase 归因、下次三条改进
为什么现在学

这是很多人从没走到的环节，也是「写过代码」和「交付过软件」的分界线。

动手任务
  • 打包 zip，在另一台机器（或另一份全新 IDEA 配置）按 README 装好并跑通
  • 跑一次 ./gradlew verifyPlugin，读懂报告里每条警告，把结论写进 README 兼容表
  • 请 2–3 位同学只看 README 自行安装，记录他们卡在哪一步
  • 写 CHANGELOG 与 3 分钟演示脚本并录屏
  • 写一页复盘：时间估错在哪、卡最久的坑、下次怎么改
检验标准
资料

IntelliJ Platform SDK「Publishing a Plugin」「Build Number Ranges」「Verifying Plugin Compatibility」；README 写法可参考任意你喜欢的开源项目。

预期卡点

兼容区间写错导致目标 IDE 显示「不兼容」；README 里默认读者知道你知道的一切。检验方法很简单：找一个没参与过的人，让他只靠文档操作。

常见坑速查表

现象多半是
Gradle 同步失败 / 依赖拉不到抄了 1.x 的插件 ID；漏了 defaultRepositories()；JDK 版本与目标平台不匹配
菜单项 / 面板不出现plugin.xml 没登记、包名写错、依赖模块（如 com.intellij.java）未声明
插件显示「不兼容」误写了 untilBuild 上限把新版 IDE 挡在外面；sinceBuild 与真实分支号对不上（2025.3 对应 253）；构建号不能编造
verifyPlugin 构建失败2.15.0 起默认严格：兼容性问题 / Internal API / Override-Only API 会直接失败。正确做法是换回公开 API，不是调低 failureLevel 掩盖
目标平台依赖解析不到2025.3+ 官方产品类型调整，intellijIdeaCommunity() 已不适用，改用 intellijIdea()
IDE 卡住不动在 EDT 上发了网络请求或做了重活
调模型报 404 / 模型不存在还在用已弃用的 deepseek-chat / deepseek-reasoner
模型输出格式乱没开 json_object，或 prompt 里没明确要求 JSON；缺字段校验
重启后数据丢了用了普通字段或临时文件，没走 PersistentStateComponent
Key 出现在仓库里硬编码或写进配置文件；应放 CredentialStore，并把相关文件加入 .gitignore

每周自检（三句话就够）

  1. 这周留下了什么可检查的证据？（文档、测试、tag、可运行的 Demo，任一即可）
  2. 这周卡最久的是什么，我写下来了吗？
  3. 下周要做的那一件事，能不能在两周内演示给别人看？

三个问题都答得出来，节奏就没跑偏。答不出来时，先停下补证据，别急着往下写代码。

最后一句：这份路径里没有一项知识是「天才才学得会」的，它们只是需要按顺序、各花一两周。你愿意投入时间，就已经满足了最难的那个条件。剩下的交给节奏 —— 每两周一个能演示的东西，14 周后你会有一个从规格到复盘都完整的项目。
